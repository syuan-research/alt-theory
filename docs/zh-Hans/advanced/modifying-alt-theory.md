# 修改 Alt Theory 及其扩展边界

Alt Theory 开源——软件 MIT，原创文档与 agent 资产 CC BY 4.0。你可以阅读、构建、更改全部。本页关于接缝在哪：设计预期哪些变更，哪些意味着你在维护 fork。

## 为变更设计的接缝

按你伸手多远的大致顺序：

1. **资产** — 技能、角色、soul、知识库、指令
   （[上一页](customization-without-changing.md)）。是数据，不是代码；升级安全。
2. **配置** — 提供商、模型、按模式技能启用、优先级。同样升级安全。
3. **底层 Pi 生态** — 应用嵌入 Pi agent 运行时，因此以 Pi 生态资源存在的能力（包、扩展、工具）是新 agent 能力的预期路径——在那里构建或采用，而不是教应用核心新把戏。
   两个边界成立：包必须使用嵌入运行时的库（要求不同 Pi 核心的包会被禁用并有可见诊断，不会静默加倍），且应用安全层始终在回路中——无论哪个扩展提供了工具，它都中介工具执行。
4. **应用本身** — 后端、前端、打包。任你改（MIT），并诚实承担后果：你拥有与上游变动的合并，alpha 阶段变动很快。

## 扩展姿态，直说

两个有意决定塑造以上一切：

- **无环境漫游式扩展加载。** 应用不会自动加载环境中存在的任意扩展；扩展仅在应用显式注册处加载。这是安全与可预测决策——对话的能力是其配置所说的，不是机器上碰巧装了什么。
- **受信任软件边界。** 扩展与工具以你的用户权限执行。策略层约束*操作*，但没有任何策略能使未受信任的扩展安装变得安全。你往运行时加什么，就是在信任什么——请据此审计。

## 源码构建的实践说明

- 仓库 README 载有当前构建/测试命令
  （[安装页](../start-here/install-and-launch.md) 有简版）。
- 后端测试套件与前端类型检查是变更后的快速诚实检查；用修改后的构建做真实工作前请先跑。
- 架构文档在仓库 `development/architecture/` — 正是为这类读者写的。
- **源码布局与代码结构**问题，请指向公共 GitHub 仓库（`syuan-research/alt-theory`）及其中的
  `development/architecture/`——不要只靠应用内 Helper 文档。
- **纯 agent harness / Pi 引擎**行为（包、TUI 习惯、底层会话协议），用 [Pi](https://pi.dev) 文档。Alt Theory 嵌入 Pi；产品特定策略与 UI 留在这些文档中。

## 若你构建了什么

资产层设计为可旅行（尤其技能——跨 harness 可用）。若你构建的技能、角色或知识库超出自己的设置有价值，分享成本只是一个文件夹。对产品本身的变更，仓库的贡献指引是入口；alpha 阶段产品最受益于描述真实研究使用的 issue。
