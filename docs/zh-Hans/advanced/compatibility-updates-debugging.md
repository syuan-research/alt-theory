# 兼容性、更新与集成调试

维护页：alpha 期间更新可能改什么，以及如何诊断不再正常的集成。

## alpha 兼容策略，诚实说

在首个非 alpha 发布前，产品对自己持守这些规则：

- **用户数据从不会因更新受损。** 对话、记录及其出处始终保留。此承诺没有 alpha 星号。
- **资产仍可能变化。** alpha 构建可能重命名或移除内置资产（角色、soul、技能）。记录的资产在当前构建中不复存在时，对话回退到当前默认——**可见地**：重新打开时显示通知，点名记录了什么、现用什么。静默替换视为缺陷。
- **界面与配置仍可能移动。** 发生时发布说明会写。

从首个稳定版起，记录的资产跨更新持续解析；届时本节将修订。

## 更新

- **打包应用**：安装新构建；数据目录与应用分离，原样延续。
- **源码构建**：拉取、重装依赖、重建，并重跑后端测试作诚实检查。
- **任何更新后**，值得一分钟：扫一眼变更日志，重新打开最近对话（若你用过的东西被重命名，资产回退通知会出现在此），若依赖优先级行为则检查「设置 → 技能」。

## 调试集成

当定制设置行为异常——技能不再触发、模型表现与昨天不同、对话加载了意外资产——应用保留足够记录，按对话回答*实际发生了什么*：

- **加载了什么**：每条对话在创建时记录组装的确切资产——soul、角色、KB、技能及其来源（内置 / 你的 / 项目）、模型与提供商——带内容哈希。「本对话实际拿到了我技能的哪一版」有存储答案。
- **此后改了什么**：配置变更与恢复时回退作为事件与对话一起记录，因此创建至今的漂移可检查，而不是推断。
- **它做了什么**：转录的工具行本身就是日志——每次读、命令与技能加载，按轮次。

可行诊断顺序：

1. 在**新对话**中复现——多数「变了」报告是陈旧打开对话 vs 新对话设置。
2. 对照期望检查对话的**已加载资产记录**（对的技能？对的来源？对的模型？）。
3. 检查「设置 → 技能」中的**优先级与启用**（按模式！）。
4. 检查**应用外的生态**：harness 共享技能文件夹变了吗？提供商下线了模型吗？附加文件夹中的项目技能在遮蔽全局技能吗？
5. 然后才怀疑构建——并把复现带到
   [报告](../help/releases-and-further-help.md)。

## 回滚

- **资产与技能**：它们是文件——把自己的放在版本控制下（`~/.agents/skills` 的 git 仓库几乎零成本），回滚就是 checkout。
- **应用**：打包构建可重装旧版；源码构建检出上一标签。数据目录在 alpha 线内前向兼容；回滚应用不会回滚你的对话。
- **已迁移配置**：迁移副本是普通配置文件——引导流程可重跑，先前状态就是实验前提供商文件所说的（实验时请保留副本）。
