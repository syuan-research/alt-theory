# Decision record — communicative agent team (v1.3.0-alpha.5 M1)

Status: design settled 2026-07-28 (M1 complete) — implementation is alpha.5
M2. Substrate facts and baseline verified against code; comparisons
source-verified via research subagents (Codex/Grok CLI report;
@tintinweb/pi-subagents and pi-crew source reads).

## Goal

Give the main Alt Theory agent a small communicative team: it can delegate a
bounded task to a child worker that is a real persistent conversation, keep
working, exchange addressed messages with it while either side runs, be woken
by its completion even after stopping, and hand the user direct access to the
child at any time. Owner contract (locked in the alpha.5 plan): children are
background-by-default real sessions, inspectable in the right rail,
promotable to full conversations, user-messageable; model choice is initially
relative (`unspecified-lower` / `same` / `unspecified-higher`) resolved only
from models already configured and usable.

## Behavioral baseline — Claude Code / Claude Agent SDK

The owner named Claude Code as the reference for parent-child communication.
The relevant observable contract:

- **Spawn**: an `Agent` tool the model calls with a task prompt plus an agent
  type; the child starts with a fresh, bounded context containing only the
  prompt (context packet), not the parent transcript. Background by default;
  a synchronous mode exists for results needed before continuing.
- **Completion wake**: the parent receives a task notification when a child
  finishes, delivered into the parent's NEXT turn — including after the
  parent had stopped; notifications queue rather than vanish. The parent is
  told never to fabricate a pending child's result.
- **Continuation messaging**: `SendMessage` addressed by child name/id
  continues a live or completed child with its context intact — the child's
  identity and history persist across messages.
- **Task board**: shared TaskCreate/TaskUpdate/TaskList tools give
  parent and children a durable, inspectable work ledger with ownership and
  blocked-by edges; the harness (not the model) owns delivery of task state.
- **Result discipline**: a child's final message is data for the parent, not
  user-facing prose; the parent is instructed to relay what matters.
- **Isolation options**: per-child worktree/sandbox when children mutate
  files concurrently.
- **User visibility**: the user can watch any child's transcript live and
  interject; interface affordances (fleet views) treat children as sessions,
  not hidden processes.

Design-relevant consequences: (1) the spawn tool and the notification path
are the whole minimal surface — everything else (status, messaging, board)
is additive; (2) wake-on-completion is a queue owned by the harness, which
is what makes a stopped parent safe; (3) children as real sessions is what
makes user interjection and promotion cheap.

## Alt substrate facts (verified, file:line)

- Children as sessions already exist: `createRelatedSession`
  (`web-server/session-service.ts:2008-2044`) creates `side` (history fork)
  or `helper` (fresh context) children with a `forkedFrom` header;
  `promoteRelatedSession` (:2046-2068) flips purpose to `fork`.
- Sessions are owned server-side by SessionService and run with zero
  attached clients; each WebSocket connection attaches to exactly one
  session (`web-server/server.ts:1946-1961`) — background execution is
  substrate-native.
- The right rail already opens a per-child WebSocket with transcript,
  status, approvals, and a usable composer (`frontend/src/components/shell/
  InspectorPanel.tsx`) — user-messaging a child is substrate-supported.
- Run lifecycle is recorded per turn in run records (accepted / completed /
  failed / aborted / superseded) with session events in `recordsDir`
  (`session-service.ts` runPromptWithLineage, alpha.4/alpha.5 M0 semantics),
  giving children durable, inspectable state for free.
- M0 (alpha.5) guarantees mid-turn continuity for every session — children
  inherit break-point retry and never lose completed work on transient
  errors.
- What does NOT exist (alpha.4 audit, reconfirmed): any model-invocable
  spawn/status/message/wait tool; any system-prompt contract telling the
  model delegation exists; parent-child message envelopes; a wake/notification
  queue; lifecycle states surfaced in the parent conversation; the
  Edit-and-branch child shell (backend attaches the main connection to a
  fork while the rail shell expects side/helper — empty rail, locked center).

## Comparison — Codex CLI / Grok Build CLI (research report 2026-07-28)

Source-verified from `openai/codex` (Rust) and `xai-org/grok-build` docs; full
report in the session research file `cli-agent-team-contracts.md`.

- **Codex multi-agent v2** is the closest existing shape to the owner
  contract: `spawn_agent` (message, task_name, agent_type, fork_turns,
  model, reasoning_effort) / `send_message` (deliver, no turn) /
  `followup_task` (deliver + trigger turn, optional interrupt) /
  `wait_agent` (bounded-timeout, returns which agents have updates, ends
  early on steered user input) / `list_agents` / `interrupt_agent` /
  `close_agent`. Background by default; the spawn description explicitly
  tells the model to keep working and wait sparingly. Completion wake = a
  synthetic **user-role** `<subagent_notification>` fragment injected into
  the parent conversation. Children inherit the parent's *effective* config
  with sandbox/approval policy re-derived at spawn time. User can open and
  steer any child thread (`/agent`).
- **Grok Build** is the cautionary contrast: blocking spawn by default,
  subagents "largely observational" (no mid-run messaging), resume only for
  completed children, hard depth cap 1. Its good ideas: `capability_mode`
  four-way tool restriction, worktree isolation as a spawn flag, and honest
  silent-wake handling (a failed wake-turn still leaves a "Turn failed"
  line "so a standing instruction never stops executing invisibly").
- **Claude Code / Agent SDK** (baseline above): background by default,
  strict context isolation (child sees only the prompt packet), completion
  notifications queue for the parent's next turn, `SendMessage` continues a
  named agent with context intact, transcripts persist separately and
  survive compaction.

## Comparison — Pi ecosystem subagent extensions (source-read 2026-07-28)

Two real extensions read in depth (`tintin-findings.md`, `crew-findings.md`):

- **`@tintinweb/pi-subagents` 0.14.3** — in-process children via
  `createAgentSession` in the same Node process. Tools: `Agent` (prompt,
  description, subagent_type, model, thinking, max_turns,
  run_in_background, resume, isolation:"worktree"), `get_subagent_result`
  (wait/verbose), `steer_subagent`. **The wake mechanism that matters**:
  on background completion it calls Pi's own
  `pi.sendMessage({customType:"subagent-notification", ...},
  {deliverAs:"followUp", triggerTurn:true})` — the host-SDK flag that makes
  an idle parent start a new turn. Completion nudges are debounced and
  group-batched; a synchronous `get_subagent_result` cancels the pending
  nudge. Concurrency queue (default 4) for background spawns; foreground
  bypasses. The human can open a live child viewer and steer or stop it
  directly (`session.steer()` — same primitive as the tool). Limitations vs
  our contract: children are in-memory objects, not durable resumable
  sessions (resume = live-object only); no child→parent mid-run push; no
  nesting.
- **`pi-crew` 0.9.51** — subprocess-first (`pi --mode json -p`), heavy
  action-enum `team` tool plus Agent aliases. Its durable state layout
  (manifest/tasks/events JSONL + crash recovery) and its parent→child
  steering file (500ms poll, sanitized, broker push as fast path) are solid
  patterns. Its defining weakness proves our design's key requirement:
  **nothing can wake an idle parent** — completions surface only as a UI
  toast and ambient context injection on the next unrelated turn.
  `steer_subagent` is a stub for subprocess children; child→parent mid-run
  exists only among same-process "live-session" peers (`irc` tool).

Takeaways: (1) in-process children + Pi's `sendMessage(followUp,
triggerTurn)` give real wake semantics with no broker; (2) durability must
come from real session files, which Alt's substrate already provides and
both extensions lack; (3) parent→child steering and user→child steering
should share one primitive; (4) child→parent mid-run push exists nowhere in
the Pi ecosystem — Alt builds it on its own envelope layer.

## Design (settled)

**Children are Alt sessions, not extension-internal objects.** A spawned
worker is created through SessionService with a `forkedFrom` header purpose
`worker` (sibling of `side`/`helper`), giving it durable records, transcript,
run phases, M0 continuity, the rail shell, promotion, and user messaging for
free. The agent-team layer adds: a model-facing tool surface, a durable
envelope mailbox, and wake delivery.

**Tool surface (parent, registered by a new vendored agent-team extension):**

- `spawn_agent({ task, name?, context?, mode?, model_tier?, wait? })` —
  background by default (`wait: true` blocks like a normal tool call for
  quick lookups). `context` is the explicit context packet (the child sees
  only it plus its own session assembly — Claude Code-style isolation, no
  parent history fork in alpha.5). `mode` ∈ `understand`/`work`, clamped by
  the parent's mode (see permissions). Returns `{agent, sessionId}` where
  `agent` is a short name usable in every other tool.
- `send_to_agent({ agent, message, start_turn? })` — one primitive with the
  Codex distinction as a flag: default delivers at the child's next message
  boundary (steer) or queues if idle; `start_turn: true` triggers a turn on
  an idle child (followup-task semantics).
- `check_agent({ agent, verbose? })` — status, last message, and the
  durable record/transcript location; `verbose` returns a bounded recent
  transcript slice, never the whole history.
- `wait_for_agents({ agents?, timeout_s? })` — bounded block that returns
  which agents have updates; ends early when the user steers the parent.
- `interrupt_agent({ agent })` — stop the child's current turn; the child
  stays messageable and resumable (M0 break-point semantics apply to its
  interrupted turn).
- `list_agents({})` — live and recently-finished children with status.

**Child-side tool:** `message_parent({ message, kind? })` — the
ecosystem-absent piece the owner's contract requires. `kind` defaults to
`update`; `blocker` marks a dependency/input request. Persists an envelope
and wakes the parent exactly like completion does.

**Envelopes.** One JSONL inbox per session (`recordsDir/agent-mail.jsonl`),
append-only, each entry
`{at, from, to, kind: "message" | "lifecycle", event?, body, delivered}`.
Lifecycle events: `spawned`, `completed`, `failed`, `interrupted`,
`input-requested`. Agent messages and lifecycle notifications are never
mixed in one entry — the UI renders them differently and the model sees the
kind. User→child messages travel the existing rail composer path (a normal
user turn in the child session), not envelopes; parent→child and
child→parent messages are envelopes delivered into the counterpart session
as Pi custom messages (Codex-style tagged fragments).

**Wake and delivery.** Owned by SessionService (which sees every child
terminal event), not by polling:

- parent running → deliver as a Pi steering/follow-up message at the next
  boundary (`getSteeringMessages` path);
- parent open and idle → `pi.sendMessage(..., {deliverAs: "followUp",
  triggerTurn: true})` starts a notification turn; that turn runs through
  Alt's normal run-record path so lineage/metrics stay truthful;
- parent not open → the envelope stays undelivered; on next open, undelivered
  mail is injected into context (pi-crew's ambient pattern) and surfaced as
  UI status lines; nothing is lost because the inbox is durable.
- A wake turn that fails still leaves a visible failed-run line (Grok's
  "never fails invisibly" rule).

**Permissions.** Child mode is clamped to the parent's: an Understand parent
spawns only Understand children; a Work parent may spawn either (default
Understand unless the task needs file work). Work children share the
parent's workspace roots — never wider — and their approval requests surface
in the child rail plus a parent status line. Clamping is re-derived at spawn
time from the parent's current session state (Codex's stale-config warning).

**Model tiers.** `model_tier` ∈ `lower` / `same` (default) / `higher`,
resolved at spawn against models configured AND usable (existing auth/config
truth): `same` = parent's model; `lower`/`higher` rank usable models by
models.dev cost metadata and pick the nearest cheaper/stronger one; no
usable candidate → fall back to `same` and say so in the spawn result.
Explicit model names and per-role presets are deliberately later work.

**Failure/retry.** Children inherit M0 wholesale: auto-retry with preserved
work, break-point continue, sanitized context. A child that exhausts retries
persists `failed` + last error in its lifecycle envelope; the parent decides
(retry via `send_to_agent(start_turn)`, or spawn fresh). No automatic
parent-driven respawn in alpha.5.

**Workspace conflicts.** Alpha.5 documents shared-workspace hazards in the
spawn tool description (tell the model to partition files) and serializes
nothing; worktree isolation is banked (Alt's audience is not git-first, and
the write-guard already prevents out-of-root damage). ponytail: revisit only
if real collisions appear.

**Depth and concurrency.** Children cannot spawn (`spawn_agent` absent from
child tool sets — tintin's exclusion pattern); background concurrency cap 3
with a FIFO queue, foreground bypasses (tintin's model).

**System-prompt surface.** One short "Delegation" section in both modes'
assembly: the tools exist, children are real conversations the user can see
and join, work continues in the background, never fabricate a pending
child's result (Claude Code's rule), wait sparingly (Codex's rule).

**UI.** Children appear under Related conversations as `worker` children
with live status dots (reusing run phases); parent transcript shows compact
lifecycle lines (spawn/complete/fail) and envelope messages as addressed
bubbles; the child rail composer stays usable (user joins any time);
promote works as today. The Edit-and-branch gap is fixed by routing that
flow through the same worker shell states instead of the bare fork attach.

**Lifecycle ownership.** SessionService owns child lifecycle (spawn via
substrate, terminal events, wake delivery, cleanup); the extension owns only
the model-facing tool surface and translates tool calls into SessionService
operations over a narrow injected interface. No second manager process, no
broker, no subprocess spawning.
